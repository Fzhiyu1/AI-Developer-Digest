# AI Daily Paper — 仓库深度研究

> 此 prompt 由 research.sh 按仓库并行调用，每次只研究一个仓库。

## 研究方式

通过 GitHub API 获取信息（不要 clone），包括：
- 仓库元信息（star/fork/issue/语言）
- README 全文
- 目录结构
- 最近提交记录

## 分析维度

1. **项目概述** — 一句话说明
2. **技术栈** — 语言、框架、核心依赖
3. **项目结构** — 关键目录和文件（树状图只保留核心层级，不展开所有子文件）
4. **核心功能** — 最多展开 3 个核心模块，每个附一段 README 原文代码示例
5. **活跃度** — 提交频率、contributor、issue/PR。**日期必须验证**：用当前日期减去创建日期计算项目年龄，不要写错
6. **亮点与不足** — 各列 3 条，每条一句话 + 具体依据。不足部分必须包含风险评估（如单人维护、依赖闭源服务、无测试）
7. **竞品对比**（必写）— 列出 2-3 个同类项目，用表格对比核心差异（如 stars、功能覆盖、部署方式）
8. **应用方向分析**：
   - 该项目解决了什么核心痛点（1-2 句）
   - 最佳应用场景（最多 2 个详细展开，其余一句话带过）
   - 对个人开发者 vs 企业分别有什么价值（各 2-3 句）

## 硬约束

- **篇幅限制**：报告总长 **150-200 行**。超过 200 行说明内容不够精炼。重点写分析和判断，不要堆砌原始数据或罗列所有功能
- **禁止编造**：所有数据（star 数、下载量、性能指标）必须来自 API 查询结果或 README。禁止编造"降低 70% 成本"、"提升 50% 效率"等无依据的数字
- **代码示例**：只能引用 README 或 examples/ 中的真实代码片段，不要自行编写假的 API 调用示例
- **禁止主观评分**：不要输出「推荐指数 ⭐⭐⭐⭐⭐」「评分 5/5」等任何形式的打分。用事实说话：star 增速、issue 响应速度、文档完整度、测试覆盖等客观指标
- **扩展方向务实**：最多列 3 个扩展方向，每个必须说明技术可行性。不写「策略库市场」「RL 优化」等高度投机的方向
